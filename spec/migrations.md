# Save continuity and migration

`MIG-01` — Preserve historical prototype/setting IDs, level boundaries, effective native effects, hidden carriers and relevant persistent state before attempting runtime recovery. Same ID alone is insufficient if effect values, targets or starting levels change.

A data-stage generator cannot inspect the player's save. Runtime code cannot reliably reconstruct state already discarded by engine loading. Missing a required historical technology must not be treated like an absent optional new addition. [Lifecycle](https://lua-api.factorio.com/latest/auxiliary/data-lifecycle.html)

## Baseline and upgrade paths

The principal predecessor is the exact published 4.7.3 package for the same engine family, supplemented by the known historical migration boundaries below. Preserve prior release variants by their hashes where relevant; version text alone does not identify previously reissued bytes. Distinct older upgrade boundaries retain their previously promised scope or receive an explicit documented bridge decision. Never recommend downgrade as the automatic inverse of upgrade.

Private incomplete slices use disposable worlds only. Do not load and resave a real full MIR factory with a one-technology replacement package. Full-save migration qualification starts only after all relevant definitions and runtime bridges exist.

The published F200 Base `recipe-prod-research_science_pack_productivity-1` six-recipe public row is intentionally present in F210 Base with the same authored ID, settings, cost and effects because both targets support its named native recipe-productivity effects; this narrow `MIG-01` compatibility correction restores the historical identity to fresh F210 Base worlds as well as preventing engine-load loss for earned F200 levels. It adds no new identity or runtime carrier and leaves F210 Space Age unchanged. The [C563 Base save hop](evidence/full-catalogue-f200-f210-c563-native-chain-r01.json) now demonstrates the exact published4.7.20003/2.0.77 to source1c90/C563/2.1.23 transition, retained54 level-backed public rows, actual source/successor gear labs and two independent cold reloads. The later [8F protected-save successor](evidence/full-catalogue-f200-f210-8f-native-chain.json) consumes the same unchanged published source save on exact2.1.23, retains54 seeded rows and42% queued/27% detached work, completes one new successor gear lab and preserves the successor save through two separate read-only cold reloads. Its carried source-lab count is not additional work. These results retain their original C563 and8F package/controller identities; they do not qualify later changed inputs, other mod/DLC closures or simultaneous settings/provider changes.

The one-time F200-to-F210 cap reader additionally admits the exact structured-V3 versions observed in the [published MIR4 archive inventory](inventory/migration-origins.json), from4.2 through4.7.3. A matching package-change event and the exact current destination version permit the existing settings-derived reader for currently admitted named research and native worker tails. Always retain the ordinary current-target reader first: the actual stable4.2 F210 ZIP reports version4.2.20000 internally, so a version label cannot identify the source engine or replace per-row provenance. Current MIR5 ownership wins across both readers, including a literal-false decision for the currently admitted worker owner. Policy, visibility, foreign-disablement, native-effect and one-time checks remain binding. Construct the bounded predecessor map only for that first recognized V3 configuration, never ordinary parsing or cold loading. Host controls demonstrate earlier published tuples, the F210 label collision, unknown-version refusal and current/foreign worker boundaries; actual historical finite-cap upgrades, earned effects/new labs, saved successors and two cold reloads remain required.

Published F2004.7 did not persist the old competing-productivity preference, and the configuration event reports only whether any startup setting changed. On the first4.7.20000/.20001/.20002/.20003→MIR5 upgrade, an earned named overlap without its own valid MIR5 credit ledger must refuse if startup settings changed and a known provider is current or being removed. Upgrade with startup settings unchanged and save once before changing the preference in a later MIR5 configuration. Ordinary provider-free upgrades are unaffected. The [exact4.7.20002 native chain](evidence/legacy-preference-transition-native-chain.json) verifies refusal and both two-step directions, actual successor labs, earned effects, foreign queue and two cold reloads at its recorded source. The4.7.20003 guard extends the same rule because the inspected4.7.3 hotfix retains the preference-history producers; its opposing host control covers both inclusion states without ledger/native writes on refusal. This source-level guard does not qualify an unpinned4.7.3 archive: exact predecessor bytes and its actual successor save/two-reload route remain required. Other predecessor binaries and provider mixtures retain their affected qualification obligations.

## Finite transition policy

Record direct, staged, refused, unavailable and unresolved routes against their exact inputs instead of treating every engine/DLC/provider permutation as supported. The maintainer's explicit origin coverage below defines the migration gate; it does not imply arbitrary engine/mod combinations. A later source change needs a consumed-path applicability review and any affected native scenario; unchanged evidence keeps its original name and verdict.

| Route | Policy and current evidence boundary |
|---|---|
| Published MIR4.7 to MIR5 on the same retained engine | Intended direct upgrade for the complete admitted subset; every final package still needs its applicable earned/current/queued/suspended/runtime checks. |
| Published F2004.7.3 Base to F210 Base | The exact C563 route and separate8F successor above passed with the protected published source save; other profiles and later changed inputs require execution or justified VER-06 reuse. |
| Published F1104.7.3 to F200 | [r05](evidence/f110-f200-published-source-r05-native-chain.json) passes the protected F110 source stage. The separate [a1fd/8BA recovered successor](evidence/f110-f200-a1fd-successor-recovery-chain.json) passes one actual successor lab, seeded-state preservation, save and two cold reloads on2.0.77. Its outer caller adverse remains preserved; final changed inputs still need execution or justified VER-06 reuse. |
| First4.7 upgrade with changed startup settings and an earned known productivity overlap | Refuse when the former preference is unknowable; use the unchanged-settings first upgrade and saved/reloaded MIR5 intermediate before a later preference/provider change. The exact4.7.2 two-step record above does not qualify every4.7.3 closure. |
| Add/remove Space Age or a productivity provider | Require the named admitted route and separate native evidence for that closure. Preserve original saves; neither ordinary reloads nor an unrelated successful profile establishes this axis. |
| Remove MIR/provider, save, then readd | Absence cannot execute that mod's preservation code. Do not promise reconstruction of levels/state already discarded by the engine; use an original backup or an explicitly qualified bridge. |
| F018/0.18.47 experimental GitHub-only edition | Preserve its package metadata/version floor and use shared F100 mechanisms or compatible inputs only where their F018 contract matches. Its target-specific check is an actual0.18 native load/crash smoke; it has no stable-release save, modpack, science, client or performance campaign. An F100 result is not an F018 pass, and missing0.18 inputs do not block the nine stable editions. |
| F001–F012 additions | Build/loader feasibility and native save continuity remain separately recorded best-effort obligations. No direct-save-hop promise follows from a build. |

For a refused or unqualified upgrade, retain the original save and its matching archives/settings, test only a copy, and use a named qualified intermediate route when one exists. Do not recommend a downgrade or a remove-save-readd cycle as an inferred inverse migration.

## Required origin coverage

The [origin inventory](inventory/migration-origins.json) retains the exact maintainer request, separate lock-repair answer and implementation interpretation under `maintainer_scope_clarification_2026_10_28`. Original wording and interpreted requirements remain distinguishable.

`MIG-05` — The maintainer's 28 October 2026 clarification supersedes the earlier requirement to complete a separate historical campaign for every published patch before 5.0.0. The release must qualify exact published MIR 4.7.3 saves for every stable supported edition with an actual predecessor, plus older saves representing each materially distinct known breaking contract: technology identities, native effects/progression, settings, migration-name history, saved-state schemas and disablement/contribution ownership. Preserve the complete modern-origin inventory and the goal of useful direct upgrades from MIR 1.0.0 onward on 2.0/2.1. Unknown or ambiguous older histories may remain explicitly unverified/deferred; never guess a repair or count that disposition as a pass. A known reproducible regression in a required current or selected boundary route remains a release blocker.

Group older releases by their actual consumed saved-state contract, not only major/minor/patch labels or one identical writer file. A patch with a changed contract needs its own affected case. Select useful representative protected saves for unchanged contracts, preserving exact source/archive/engine/settings identities. A representative pass qualifies its tested route and demonstrated contract only; it does not become a native pass for every unrun tag. The 1.0.0 tag really targets Factorio 2.0, and the inventory includes non-master/backport releases; neither a small version number nor omission from the master changelog justifies discarding it.

| Origin and destination | Required qualification |
|---|---|
| Exact 4.7.3 to 5.0.0, same stable edition | Each actual published predecessor; Base/Space Age where supported and affected settings/provider/mod closures. |
| Known distinct older MIR 1–4 contracts on 2.0/2.1 | Protected representatives covering each actual identity/effect/settings/schema/ownership change, including material published-byte variants. Direct MIR upgrade requires no invented intermediate release. |
| Selected 2.0 sources brought forward to 2.1 | Separate 2.1 successors for the required predecessor and known distinct boundaries, with original engine/package and necessary engine bridges recorded. No fabricated 2.1 predecessor or downgrade promise. |
| Other older modern origins | Retain inventory, saves, mappings and exact statuses. Continue inexpensive relevant coverage; defer uncertain/unavailable cases with an explicit reason and support limit, never a guessed recovery or implied pass. |
| Stable target without a published 4.7.3 artifact | Record absence and use the latest actual relevant predecessor; qualify the route instead of inventing an artifact. F018 retains its experimental contract. |
| MIR 5-or-later stable origins | Retain the tested forward-upgrade obligation for engine-valid stable origin/candidate pairs. This older-history clarification does not waive future MIR 5 save continuity. |

The nine stable-edition obligations, applicable current native/save/client/performance gates and cumulative migration-file preservation remain unchanged. F018 and earlier best-effort editions retain their separately stated limits. Historical checkpoints keep their original requirements as history; they do not restore the superseded every-tag 5.0.0 gate.

Recover the finite origin list from published tags/releases and their actual package metadata and hashes. For every origin record the source commit, engine eligibility, archive identity, relevant JSON/Lua migration names and contents, required mods/settings, save identity and any unavailable input or known historical defect. Distinguish a published artifact from a reconstruction of its tagged source. Keep this coverage with the existing inventories, profiles and exact evidence; do not add a production history database, generic migration planner or another assurance framework.

Reuse protected existing saves and trusted exact-input receipts before generating new source worlds, including saves from older engine patches and earlier engine families. For unqualified routes, start with the currently installed 2.0/2.1 engines and available dependency archives; record their exact versions/hashes and any differences from the save's original mod/settings closure. Preserve the historical MIR origin's identity. A passing run qualifies its actual tested inputs, without pretending to reproduce a different historical dependency closure. Before fetching older dependency versions, classify suspicious differences against source-fixture expectations, engine/API changes and changed upstream behavior; isolate the affected input only when needed. Unsupported save formats use the necessary installed engine bridges on disposable copies. Missing original dependency archives alone do not block this first evaluation, and unexplained earned-state loss never becomes an accepted expectation.

Each selected qualification route needs an actual original-save to candidate-save to two-cold-reload route under `MIG-03`, with new native research and the expected earned effect where research is supported. Check completed/next levels, partial and queued/suspended work, native and scripted contributions, settings, caps and disablement ownership, relevant entities and unrelated force state. Select boundary states and affected mod closures explicitly; a fresh-world load or one 4.7.3 save does not qualify all older origins. Shared fixtures may exercise common checks, but different origin saves remain different native cases. Reuse a successful frozen source stage without recreating or overwriting it.

An engine that cannot read the origin save format needs an explicit engine bridge; this is distinct from requiring an intermediate MIR installation. An old mod that cannot create or load a valid source save remains an evidenced adverse/unavailable route. Under the 28 October decision, an uncertain older route may be deferred after recording the actual obstacle, preserved inputs and support limit; a required current or known boundary failure still needs correction. Preserve its original bytes and failure instead of patching the published archive and calling it historical qualification. The existing 4.2.1 loss guidance and 4.7 preference-history ambiguity remain real limits: no migration can infer erased earned state without surviving evidence.

## Ambiguous researched-planet locks

The maintainer selected preservation with explicit repair on 28 October 2026. A researched-but-locked location without a surviving ownership marker does not authorize MIR to override another mod's lock. Keep ambiguous state unchanged by MIR and offer only an explicit operator-selected repair of a known researched grant. Do not unlock all researched locations automatically, infer lost intent from a version label, or add a recurring repair handler.

The [exact R05 no-helper successor](evidence/discovery-recovery-a575-native-chain-r05.json) passes from protected published3.2.0 saveEC0E on a575/7CE and Factorio2.1.23/8DC: player Vulcanus is unlocked, the foreign location stays locked, queued42% and detached27% work survive, one new gear lab completes, and the successor save passes two unchanged-byte cold reloads. The original R01/R04 refusals remain preserved; R05 avoids changing the queued iron research's unit cost. This demonstrates one exact native route without the proposed automatic helper, which remains unmerged. It does not qualify currentc74, inherited3.2.1 histories or an ambiguous foreign lock. MIR cannot reconstruct a lock already discarded by engine loading before callbacks. The [one-time recovery procedure](../docs/support.md#researched-planet-still-locked) selects one force/location and verifies its current researched native grant; it is an operator choice, not a migration pass.

## Migrations themselves

The [six original archive observations](evidence/historical-boolean-cap-archive-metadata.json) and [two F200 observations](evidence/historical-boolean-cap-f200-archive-metadata.json) establish that MIR2.5.10/2.5.11 F200, MIR3.2.10/3.2.11 F210 and MIR4.0/4.1 F200/F210 shipped policy-v1 boolean cap controllers. The four MIR4.0/4.1 ZIPs differ from their tag-source controller. Their literal positive disable marker proves MIR observed enabled research and disabled it; absent or false markers grant no enablement right. An optional visibility boolean proves only its own field. Read this component once on configuration change, against current admitted identities/settings/source classes and the known historical operations, without importing the retired implementation or inventing structured-V3 fingerprints. Preserve current MIR ownership and changed foreign state; later indistinguishable foreign writes retain `RUN-03` limits. The archive probe and host controls do not establish native save-upgrade acceptance: each affected actual source/candidate/save/two-reload route remains required.

`MIG-02` — Inventory existing JSON/Lua migrations by filename, purpose, required predecessor and imports. Factorio remembers applied names and runs JSON before Lua migrations. Do not rename filenames mechanically during repository cleanup. Decouple required historical logic from retired imports without retaining a whole old subsystem. [Migrations](https://lua-api.factorio.com/latest/auxiliary/migrations.html)

Small state transformations are idempotent. Keep the existing storage/global namespace and contribution baselines where necessary. Do not reset every force/technology, clear `mir` storage or grant invented levels to repair an unexplained failure. Writing native `level`/`researched` can itself change benefits/enablement; test effective state. [LuaTechnology](https://lua-api.factorio.com/latest/classes/LuaTechnology.html)

`MIG-06` — Maintain one shared cumulative migration set and narrow engine adapters. Audit every historically published migration filename, ordered transformation, predecessor schema, import and affected identity before deciding to retain, replace its internals or retire its implementation. Preserve applied filenames and live rename/carrier obligations. Required recovery must be self-contained or use current bounded runtime helpers; it must not import a retired compiler, Generator or old whole-version source tree. A blanket restoration of every historical Lua script is not acceptable: a previously applied migration is skipped, while a newly added filename can run against much newer saves and on mod addition. Test both histories before shipping a recovered step.

Prefer preserving an unchanged native identity to renaming it. Where a rename is necessary, retain the exact JSON mapping and test the ordered composition of all relevant mappings, including a save that already applied an earlier mapping. Use Lua only for necessary saved-state transformations with explicit schema/input guards and a bounded set of MIR-owned entries; preserve foreign contributions and invalid-object handling. Reconciliation may be idempotent, but that does not make replaying an old exactly-once engine migration safe. No repeated world/entity scan or per-tick migration loop follows from cumulative support.

Every future release reviews its identity, schema and setting changes against the retained origin matrix. Add a new stable migration filename only when a new transformation is necessary; do not add empty files per release or repurpose an already applied name for work that existing saves must execute again. Keep independent package-membership/rename-chain/schema controls and native direct-upgrade fixtures. Record source-save, candidate-save and reload hashes in the existing evidence chain. Historical source and large save custody stay outside player packages; only required live migration code and mappings ship.

Establish the historical recovery inventory, saved-state expectations and protected origin-save baseline for 5.0.0 once, then maintain them incrementally. Later releases add their actual identity/schema changes and new origin saves; they do not repeat tag archaeology or regenerate unchanged predecessors. Reuse exact trusted source stages and apply `VER-06` to prior results, executing the new transition and older direct-origin regressions affected by changed consumed paths. Skipped-release upgrades remain supported and tested within the required engine-valid scope; incremental maintenance does not mean testing only the immediately previous MIR release. Keep these checks in existing package/schema/native tools rather than introducing a separate migration framework or recurring player maintenance.

## Independent observation

Capture the earliest accessible loaded state before MIR compensation, then after migration and ordinary lifecycle handling. Compare completed/next levels; science/cost/effect semantics; native owner contributions; hidden carriers; queue/current research; saved progress; configured caps; disablement ownership; runtime multipliers; settings and unrelated force data.

`MIG-03` — Acceptance is original immutable save → candidate upgrade → saved candidate → independent cold reload → second cold reload, plus actual multiplayer lifecycle where affected. Same binary and upstream closures must be retained or any deliberately changed boundary isolated. State disappearance before callbacks is a failure to diagnose, not a fixture value to overwrite.

Required opponents include levels 0/2/3/7 around staged continuations; finite-at-cap and earned-above-cap; 42% partial investment where existing fixtures use it; native powder/crystal separation; unrelated scripted offset sentinels; mod removal/readdition; optional feature disable cleanup; force merges/resets; library state reconstruction.

## Cleanup is not history erasure

Delete retired implementation after obligations are recovered and replacement acceptance exists. Keep small active regression fixtures and source/hash pointers that still test current continuity. Old release branches/tags hold old design documents. Old migration filenames, real compatibility aliases, copyright and changelog entries are **live obligations**, not confusing architecture remnants to be renamed blindly.

## Determinism does not replace migration qualification

`MIG-04` — The migration input includes the save's applied migration-name history, not just its research levels. Equal complete input must yield equal output. An exactly-once engine migration and an idempotent reconciliation function have different tests. Never reset migration history as a shortcut.

Do not open and save a real full-catalogue world with a one-family experimental package. Early slices use disposable fixtures. A preserved prototype ID with changed effect recipes, initial level or per-level scalar may still lose meaning; compare the earned native/physical outcome, not only names. See [determinism](determinism.md).
