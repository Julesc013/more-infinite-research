# Fixture Workflow

Use fixtures to turn compatibility claims, bug reports, and risk cases into repeatable evidence.

The prepared [Secretas finite-continuation fixture](../../fixtures/assert-secretas-finite-continuation-hotfix/scenario.json) is consumed by [Test-MIRSecretasFiniteContinuation.ps1](../../tests/runtime/Test-MIRSecretasFiniteContinuation.ps1), with a supplied F210 4.2.2 candidate and its materialization receipt. `-PrepareInputsOnly` writes the small fixture ZIP and preparation record inside the checkout without an engine or archive library. Native mode takes explicit `-FactorioExe` and `-LibraryDirectory` bindings, verifies the selected engine/API and Secretas 1.0.37/Frozeta 1.0.1 archive hashes, and requires the candidate already installed once. It selects those inputs directly under exclusive library ownership, establishes defaults, and restores prior controls. The probe retains upstream finite levels seven/eight, checks infinite MIR level nine and its golden/promethium science, observes one engine-awarded cargo increment, and checks level ten, the earned bonus, queue and 42% progress after two reloads. Its Lua callback controls simulate the engine award solely to test oracle activation and rejection. The installed F210 Secretas 1.0.37 archive fails before gameplay on Factorio 2.1.21 because golden-biter-egg still uses the removed fuel_category item field. This upstream failure is retained as a failed native observation. Select -Target f200 to use the separate pinned 2.0.77 / Secretas 1.0.33 / pretty-frozeta 0.1.0 scenario and private assertion fixture 0.1.3; that scenario does not qualify the incompatible F210 archive or the reporter save. Both paths require an actual native pass before making a continuation or save claim.

For current F210/F200 base upgrades, [Test-MIRUpgrade.ps1](../../tests/runtime/Test-MIRUpgrade.ps1) accepts explicit `-SourceVersion 4.2.2`, the supplied candidate's `-SourceMaterializationPath`, `-SelectedTarget`, `-FromVersion 4.2.CCC00` or `4.2.CCC01`, `-ToVersion 4.2.CCC02` and `-PublishedMaintenancePredecessorManifestPath` pointing to the exact published 4.2.0-stable or 4.2.1 manifest for that selected predecessor. The native input reader authenticates the complete published manifest, asset metadata and tag, then verifies the supplied `-FromZip` in place; unrelated predecessor ZIPs are not required for a selected native case. The release custody reader still verifies all nine archives by default. Replace `CCC` with `210` or `200`; use the existing `assert-upgrade-4-0-CCC00-to-4-1-CCC00` fixture template, `-Archetype base-default` and `-Retention Always`. Omitted archetype in this mode also selects base-game controls. Source version defaults to 4.2.1 and still requires its `CCC00` predecessor. Prepare the small assertion fixture first with `-PrepareInputsOnly`; CCC01-to-CCC02 base fixtures use version `0.1.2`, while direct CCC00-to-CCC02 uses `0.1.6`, separate from the retained 4.2.1 base `0.1.1` and Space Is Fake `0.1.0` fixtures. Run against one explicit `-LocalModLibraryDirs` library with the selected archives already present and a declared resource budget. The existing runner verifies current candidate bytes and published predecessor custody, then uses direct-library activation and private output. This enables the selected base-upgrade input path; actual saves and reloads remain native work. Space Is Fake and K2 use the dedicated scenario inputs below.

The same runner accepts `-SpaceIsFake -SourceVersion 4.2.2` for either explicit `4.2.CCC00 -> 4.2.CCC02` or `4.2.CCC01 -> 4.2.CCC02` transition on F210/F200. Supply the current materialization receipt, published 4.2.1 manifest and explicit library as above; select `base-continuations` on F210 or `base-default` on F200. The existing scenario pins Space Is Fake/cr-commons to `1.0.78`/`1.0.33` on F210 and `1.0.60`/`1.0.27` on F200. Prepare the assertion fixture separately: SIF 4.2.1 retains `0.1.0`, SIF CCC01-to-CCC02 uses `0.1.3`, direct CCC00-to-CCC02 uses `0.1.7`, and base upgrades retain their separate `0.1.1`/`0.1.2` identities. Actual caller controls check both transitions, inherited oracle insertion and rejection of mismatched versions. The unchanged native oracle checks weapon-shooting-speed-7 and research-speed-7, finite anchors, science quantities, earned rewards and reloads. Its extra CCC00 manufacturing-retention case remains specific to the recorded older transition. Current SIF gameplay and saved-state acceptance require native execution; prepared inputs and controlled tests provide no such result.

The current oracle seeds earned state on the published predecessor and requires its finite first three levels, six/eight-percent powder bonus, independent ten-percent crystal owner, selected queue and completed work to survive upgrade and two reloads. Cap zero checks an already existing level-five continuation; it does not reuse the older migration claim that the upgrade introduces level four. Host callback controls test oracle rejection and cost normalization without simulating native research or save serialization. Actual current K2 execution, natural acquisition and production throughput remain unqualified.

The [joined nine-target engine runner](../../tools/commands/release/Invoke-MIR42FourTargetEngineRun.ps1) also consumes the source version from its supplied construction manifest and forwards it to the upgrade harness. For a 4.2.2 candidate, supply the published 4.2.1 predecessor manifest, explicit engine paths and library bindings, and the exact candidate/predecessor archives already installed in each library. Prepare the selected assertion fixtures separately before launching the campaign. F210/F200/F110/F100 maintenance fixtures use `0.1.1` for 4.2.1 and `0.1.2` for 4.2.2; historical F017 through F013 fixtures use `1.0.1` and `1.0.2`. For the F210 emergency catalogue check, select `-SourceVersion 4.2.2 -SelectedTarget f210 -FromVersion 4.2.21001 -ToVersion 4.2.21002 -FixtureName assert-upgrade-4-0-21000-to-4-1-21000 -Archetype space-age-native-owner`, the supplied materialization receipt and `-PublishedMaintenancePredecessorManifestPath dist/release-4.2.1/assets/mir-4.2.1.release.json`. The selected native reader authenticates that unchanged manifest and verifies the supplied predecessor archive directly. For direct `4.2.21000 -> 4.2.21002`, use the retained `fixtures/release-inputs/mir421-published-420-manifest.json` and the verified published CCC00 archive, not an arbitrary same-version development ZIP. Use `-PrepareInputsOnly` first: the CCC01-to-CCC02 complete-state fixture uses `0.1.16` and direct CCC00-to-CCC02 uses `0.1.17`, separate from base and Space Is Fake. The native runner must observe the complete-state marker during upgrade and both reloads, checking every force's existing technology identities, definitions (including effects, science, prerequisites, costs, caps, order and visibility), earned levels, availability, saved and active progress, recipe and direct force bonuses, complete queue and raw/imported startup settings. It exports independent source/upgrade/reload JSON snapshots under the run's private script-output directory; product recovery code must never read those evaluator snapshots. Controlled callback and marker tests reject skipped checks and lost state; they establish no native save preservation or recovery of state discarded by an earlier overwritten save. The portable source controls run through `python tests/compiler/run_emergency_catalogue_controls.py`, with `--lua-runtime-dir` when an already installed Lupa Lua 5.2 package needs an explicit local binding; no mod archives or engine are required.

1. Add or update a fixture mod under `fixtures/`.
2. Add a post-MIR assertion fixture when behavior must be proved after MIR runs.
3. Register the fixture in `.mir/fixtures.yml` when it backs a durable claim.
4. Update `.mir/compatibility.yml` or the canonical claim JSON if public wording changes.
5. Run static validation first, then runtime validation with a Factorio binary.

Keep fixture names aligned with the behavior they prove. In particular, reduced-target setting visibility belongs to `reduced-settings-surface`; it must not be folded into `settings-profile-roundtrip` when the codec is not shipped on that target.

Compatibility campaign scenarios use schema 2 records in `validation/scenarios/manual.json`, `local-library-scenarios.json`, and `local-library-scenarios-2.0.json`. Do not pass setup policy only through PowerShell. The record must declare targets, kind, group, setup, roots, settings, expected plan boundary, timeout, claim level, and notes. Static validation runs `tests/compatibility/Test-MIRScenarioManifests.ps1`; campaign evidence retains those execution properties next to the exact archive, source commit, dependency lock, actual roots, and result.

A reload-bearing manual scenario additionally declares `runtime_fixtures`, `required_reload_count`, `max_reload_duration_seconds`, and any `required_reload_log_fragments` in the manifest. Reloads are explicit per-scenario opt-ins, limited to two, and preserve distinct stdout, stderr, Factorio-log, duration, and save-hash evidence; scenarios without those fields retain the zero-reload behavior.

Older fixture archives and native receipts remain historical inputs under their original identities; these caller changes establish no fresh gameplay result. The separate [Lua version controls](../../tests/runtime/k2_imersite_version_controls.lua) execute the actual data and runtime fixture guards with supplied source strings and controlled tables; they do not simulate production or save serialization.

The [Research Library graphical runner](../../tests/runtime/Test-MIRResearchBrowser.ps1) and [personal-state lifecycle runner](../../tests/runtime/Test-MIRBrowserPersonalStateContinuity.ps1) also accept explicit `-SourceVersion 4.2.2` for `4.2.21002` or `4.2.20002` candidates. Their default remains `4.2.1`; selecting one source version does not admit a package from the other. Supply the engine and flat library explicitly, with the selected candidate and exact prepared assertion fixtures already present. The graphical runner's target values are `2.1`/`2.0`; the lifecycle runner uses `F210`/`F200`. Lifecycle `ScriptedFixture` remains F200-only and does not establish physical mouse or keyboard interaction. Host controls exercise argument binding, actual archive readers, library selection and the owned-worker protocol; graphical startup, two-client lifecycle and save acceptance still require their selected native runs.

The A04 [modern launch-return scenario](../../fixtures/assert-modern-launch-return/scenario.json) selects exact F200/F210 engines and a supplied source-4.2.2 candidate. Run [Test-MIRModernLaunchReturn.ps1](../../tests/runtime/Test-MIRModernLaunchReturn.ps1) with `-Target`, `-FactorioExe`, `-LibraryDirectory`, `-CandidateZip` and `-SourceMaterializationPath`. The candidate must already exist once in the selected library with matching bytes. Use `-PrepareInputs` once to install the small assertion fixture under the existing library lock; its only generated variation is exact target metadata. Preparation refuses different bytes already occupying the same fixture identity. It restores the previous control files and starts no engine. Normal execution reads archives directly, activates default settings and disables unselected mods through the existing library adapter. All run output stays under the checkout.

The fixture grants prerequisites, places a silo, landing pad and lab, supplies non-space inputs and power, and accelerates ticks. It changes no recipes, rocket-part counts or research-progress values. The engine must consume the construction inputs, launch a satellite, deliver 1000 space science and consume a transferred portion in the lab. A saved completed result is then independently reloaded. This is a prepared focused acceptance test; until executed, it establishes no native, graphical, upgrade or full-playthrough acceptance. [Observation-reader controls](../../tests/runtime/Test-MIRModernLaunchReturnStatic.ps1) run without Factorio. The separate [Lua controls](../../tests/runtime/modern_launch_return_controls.lua) execute the fixture callbacks with simulated engine objects when supplied its exact `control.lua` bytes; they do not simulate or qualify Factorio's production or save serialization.

A passing survivor check is not a claim that lost research history was recovered.
