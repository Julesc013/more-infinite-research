# MIR 4 release governance

This authority defines the release-custody boundary for the private `M4C02-09-24H` programme. It does not authorize source freeze, candidate allocation, production signatures, seals, tags, promotion, or publication.

The tracked state is intentionally `BLOCKED-HUMAN-SECRET-INPUT` until the maintainer supplies a secure passphrase through an approved secret channel or identifies an existing protected encryption authority. Never put a passphrase, private key, recovery plaintext, GitHub token, or Mod Portal token in the repository, a builder worktree, the publisher directory, a command line, or ordinary audit output.

## Signing authority

Create one dedicated `ssh-ed25519` key outside the repository, every builder worktree, and the root resolved by `MIR_PUBLISHER_HOME`. Use it only through the three namespaces `mir4-source`, `mir4-target`, and `mir4-ledger`. Record only the public key and fingerprint in `.mir/releases/governance/mir4/allowed-signers.json`.

Do not create the key until the protected secret authority is available. Do not substitute an unencrypted key, an empty passphrase, a reused personal key, or a key generated by a build worker.

## Protected signing ceremony

The T15 machine preparation is governed by `.mir/releases/governance/mir4/signing-ceremony-preparation.json`. It validates the fail-closed policy, root-separation and ACL contracts, the future production-receipt schema and non-evidence template, and a disposable proof-only Ed25519 recovery drill. Run the proof-only drill from a clean source commit with an explicit OpenSSH executable:

```powershell
$sshKeygen = 'C:\Windows\System32\OpenSSH\ssh-keygen.exe'
.\tools\commands\mir4\Invoke-MIR4SigningCeremonyPreparation.ps1 -SshKeygenPath $sshKeygen -RequireClean
```

The drill creates two independently encrypted AES-256-GCM fixtures with keys held only in memory, deletes the original proof-only private key before restoration, verifies the restored fingerprint and a `mir4-ledger` challenge signature, clears the in-memory key buffers, and removes all rehearsal plaintext and ciphertext. Its public receipt grants no production authority. It is a contract and implementation test, not the production encryption authority.

T16 begins only after the maintainer approves three absolute, pairwise-disjoint, separately controlled roots and their explicit custodian SIDs:

```powershell
$env:MIR_SIGNING_HOME = '<maintainer-approved-protected-signing-root>'
$env:MIR_RECOVERY_COPY_A_HOME = '<maintainer-approved-recovery-root-a>'
$env:MIR_RECOVERY_COPY_B_HOME = '<maintainer-approved-recovery-root-b>'
. .\tools\lib\mir4\SigningCeremonyPreparation.ps1
Test-MIR4SigningRootSetV1 -RepoRoot (Get-Location).Path `
  -SigningHome $env:MIR_SIGNING_HOME `
  -RecoveryCopyAHome $env:MIR_RECOVERY_COPY_A_HOME `
  -RecoveryCopyBHome $env:MIR_RECOVERY_COPY_B_HOME `
  -PublisherHome $env:MIR_PUBLISHER_HOME
```

Inspect each protected directory with `Get-MIR4SigningAclAssessmentV1`, then pass the path and exact maintainer-approved SID set to `Test-MIR4SigningPathAclV1`. The validator translates the owner and access rules to SIDs, requires the owner to be approved, requires protected inheritance, rejects inherited grants and the broad Everyone, Authenticated Users, Users, and Guests SIDs, and permits access only to the exact approved custodians. The approved SIDs are ceremony inputs; the repository intentionally contains none. The proof-only drill applies and compares the original protected private-key ACL on the clean restored fixture without recording those local SIDs.

In a protected interactive console, generate the dedicated key without a command-line passphrase:

```powershell
& $sshKeygen -t ed25519 -a 100 -C 'mir4-release-signing' `
  -f (Join-Path $env:MIR_SIGNING_HOME 'mir4-release-ed25519')
```

OpenSSH must prompt for the protected passphrase interactively. Then use the separately approved encryption authority to create exactly one ciphertext in each recovery root, confirm distinct ciphertexts, locations, and custodians, perform the clean restore and `mir4-ledger` challenge, destroy the restored plaintext, and populate a new record conforming to `spec/schemas/mir4-protected-signing-ceremony-receipt-v1.schema.json`. The public record attests root separation, owner and ACL validation, and a hash of the approved custodian SID set without disclosing configured path values. Request an exact maintainer `ACCEPTED` decision only after those checks. `spec/templates/mir4-protected-signing-ceremony-receipt-v1.template.json` is deliberately invalid as evidence and must never be edited in place into a receipt.

## Recovery and restore

After key creation, make exactly two encrypted recovery copies in separately controlled locations under the governed recovery authority. For each copy record an opaque copy identity, encryption method, ciphertext SHA-256, location/custodian class, creation time, and restore procedure. Perform a clean-room restoration into an ephemeral directory, verify the restored public fingerprint, sign and verify a non-release challenge in the `mir4-ledger` namespace, then destroy the ephemeral plaintext. Logs contain fingerprints and ciphertext hashes only.

## Allowed signers

Each active row records principal, public key, fingerprint, namespace, effective time, status, rotation predecessor and successor, and revocation reference. A signer is effective only when one active row exists for the exact principal, fingerprint, and namespace. Builders and publisher clients consume a read-only copy; they never receive the private key.

## Key rotation

1. Suspend new release intents.
2. Generate a new protected dedicated key through the same separation rules.
3. Add pending successor rows and cross-reference the predecessor.
4. Complete two recovery copies and a clean restore test.
5. Append a signed rotation event with both fingerprints to `release-ledger/mir4`.
6. Activate the successor rows and retire the predecessor at the recorded boundary.
7. Verify old signatures with the retained historical public row.

## Revocation

Create a record conforming to `spec/schemas/mir4-key-revocation.schema.json`, append a signed `Revocation` event, mark every affected allowed-signer row revoked, invalidate unsigned or later objects from the compromised authority, and name a successor only after its recovery and restore gates pass.

## Compromise response

Immediately suspend signing, sealing, tagging, promotion, and publication. Preserve logs and ciphertext without exposing secret values. Determine the earliest possible compromise time, revoke every affected namespace, inventory and quarantine derived objects, rotate credentials independently, and require a fresh independent acceptance before lifting suspension.

## Emergency release suspension

Suspension is fail-closed and can be invoked by the maintainer, the independent auditor, a failed signature or restore check, credential uncertainty, publisher-confinement failure, archive-integrity failure, or ambiguous ledger ancestry. Suspension does not rewrite or delete ledger history.

## Append-only ledger

`release-ledger/mir4` contains ledger records only, has signed commits, and rejects force-push and non-fast-forward history. Every event validates against `spec/schemas/mir4-release-ledger-event.schema.json`, names the SHA-256 of its predecessor event, and uses the `mir4-ledger` namespace. Product source is forbidden on the ledger branch.

The branch is not created while signing authority is blocked: an unsigned placeholder would misrepresent the acceptance boundary.

## Archive authority

`MIR_ARCHIVE_HOME` resolves the external archive root. Its governed subroots are `source-bundles`, `target-packages`, `release-capsules`, `proof-objects`, `publication-receipts`, `recovery-material`, `predecessor-custody`, and `rights-custody-metadata`. Builders may write only programme-scoped private objects; release custody begins only after an explicit later transition. The current Windows profile defaults to `C:\Projects\Factorio\archive`, but that machine path is not a portable normative authority.

## Publisher confinement

`MIR_PUBLISHER_HOME` resolves the external publisher root. It may contain sealed package bytes, public release records and keys, the seal verifier, publication clients, and external credential-authority metadata. It must not contain a source checkout, compiler, package materializer, package builder, mutable package staging, or private signing key. The current Windows profile defaults to `C:\Projects\Factorio\publisher\mir4`; the resolved paths and non-secret readiness state are written to ignored `.mir/local/mir4-release-governance-readiness.json`. GitHub and Mod Portal credentials remain in an external user or machine credential store; tracked records state authority and presence, never values.
