# MIR 3.3 And 2.6 Semantic Platform Roadmap

> Historical checkpoint: this proposal is preserved for provenance. The [MIR 3.3 and 2.6 convergence platform roadmap](3.3-2.6-convergence-platform-roadmap.md) is authoritative and reconciles it with the completed 3.2.3, 2.5.0, C31, and 3.2.5 planning lineage.

This roadmap begins only after exact MIR 3.2.2 and MIR 2.5.0 are frozen, independently qualified, sealed, promoted, and tagged. It consolidates the accepted future work from the 3.2.2/2.5.0 closeout audits. It does not authorize package-visible refactoring in C24 or P9.

## Release Boundary

The immediate release sequence remains:

```text
qualify and tag exact 3.2.2 C24
→ materialize exact 2.5.0 P9 from immutable tags
→ independently qualify and tag 2.5.0
→ capture both releases as behavioral baselines
→ begin the 3.3.x / 2.6.x platform program
```

MIR 3.3.x is the canonical target-neutral implementation. MIR 2.6.x is a generated and independently qualified Factorio 2.0 projection, not a separately evolved compiler.

## Platform Goal

MIR should become a small semantic platform with one canonical feature model, one settings model, one policy and conflict engine, one target-neutral compiler, one universal mutation plan, one versioned extension API, one runtime feature kernel, and one evidence graph.

The target pipeline is:

```text
TargetAdapter.capture()
→ WorldIR
→ FeatureIR
→ PolicyIR
→ typed claims
→ conflict arbitration
→ immutable resolutions
→ PlanIR
→ transaction executor
→ mutation journal and realized WorldIR
→ EvidenceIR
```

No module may mutate Factorio prototypes while it is still deciding what should happen.

## Canonical Intermediate Representations

- `WorldIR` normalizes loaded prototypes, mods, settings, unlock relationships, science/lab roles, owners, process facts, and target capabilities.
- `FeatureIR` describes target-neutral MIR features, stable identities, effects, requirements, settings, conflicts, migrations, localization, target dispositions, and test obligations.
- `PolicyIR` combines release defaults, target policy, ecosystem fragments, reviewed authorizations, user preferences, and hard safety constraints.
- `PlanIR` is the complete conflict-resolved set of prototype and runtime operations with exact operation IDs, before-state fingerprints, expected after projections, and postconditions.
- `EvidenceIR` records observations, evaluations, decisions, journals, diagnostics, compatibility maturity, and qualification results.

## Canonical Feature And Setting Authorities

Each stable or candidate feature should have one versioned `FeatureSpec`. It owns:

- Stable stream, technology, runtime, and migration identities.
- Target-neutral semantics and effect model.
- Required capabilities and target dispositions.
- Ownership, science, prerequisite, progression, cost, and presentation policy.
- Hard safety and conflict behavior.
- Player-facing setting surfaces.
- Localization contracts.
- Upgrade and removal policy.
- Required test domains and assertions.
- Backport disposition.

Each player-visible or internal setting should have one versioned `SettingSpec` that generates or validates its prototype, default, visibility, ordering, locale requirements, profile codec, target availability, documentation, fixtures, and migration behavior.

Adding an ordinary feature or setting should not require editing central orchestration, locale registries, target lists, documentation lists, or runtime routers.

## Provider And Extension Composition

Replace the broad all-purpose provider contract with composable micro-protocols:

```text
FactContributor
CandidateDiscoverer
Normalizer
PolicyContributor
QualityEvaluator
PresentationContributor
RuntimeFeatureContributor
MigrationContributor
DiagnosticContributor
FixtureContributor
```

A provider implements only the protocols it owns. Built-in and external declarative extensions use versioned manifests with explicit capability negotiation, schemas, trust classes, evidence requirements, target support, and conflict keys.

The operator registry remains fail-closed and versioned. New operators declare semantic domains, input/output schemas, target requirements, safety properties, complexity budgets, and mandatory tests. External content cannot inject arbitrary Lua behavior into the trusted compiler.

## Policy Algebra And Conflict Resolution

Compatibility packs become bundles of independent policy fragments rather than one mixed authority. Each immutable `DecisionSignal` records its ID, scope, source class, applicability, action, reason, evidence, version envelope, priority, expiry or review condition, and fingerprint.

Precedence begins with:

```text
target capability exclusion
→ hard structural safety deny
→ exact reviewed deny
→ exact reviewed authorization
→ exact mod/profile owner decision
→ explicit user preference within safety
→ promoted structural envelope
→ provider default
→ heuristic suggestion
→ unresolved diagnostic
```

Merge behavior is field-specific: safety denies dominate, owner claims arbitrate exclusively, prerequisite graphs merge under reachability checks, science sets use explicit union/intersection policy, numeric effects clamp under governed bounds, and user preferences never override hard safety.

Compatibility claims are orthogonal:

- Maturity: discovered, resolved, loads, integrity, semantic, progression, upgrade, interactive, maintained.
- Scope: recipe, family, subsystem, profile, pack.
- Behavior: diagnostic, attach, adopt, create, replace.

Public compatibility wording is generated from these dimensions.

## Universal Mutation Governance

All MIR prototype mutations flow through governed plans. Use two phases:

```text
PrecompilerNormalizationPlan
TechnologyTransformationPlan
```

Compatibility repair, permission changes, limits, sanitation, owner replacement, technology creation, scripted-effect declarations, and cleanup operations all receive exact IDs, authority, conflict keys, before-state fingerprints, expected after projections, journal rows, and completeness postconditions.

Only the transaction executor may mutate prototypes.

## Compiler Boundaries

The desired module graph is acyclic:

```text
core
→ domain/contracts
→ facts/indexes
→ graph
→ providers
→ policy/design/presentation
→ compiler planning
→ emit target adapter
→ report
```

Runtime remains a separate boundary. The top-level orchestrator may import lower layers; no lower layer imports the orchestrator, emitter, or report implementation.

Migration budget:

- 3.3.0 records every strongly connected component and forbids growth.
- 3.3.1 removes at least half of the architecture SCC edges.
- 3.3.2 reaches zero forbidden architecture SCCs.

Split `compilation_plan.lua` into input admission, sanitation planning, graph qualification, operation projection, operation validation, candidate catalog construction, selection, result planning, and a thin pure compilation sequencer.

All compilation-derived state belongs to an explicit `CompilationRun` or `CompilerContext`. Replace stringly typed context keys with a governed registry declaring schema, owner, phase, authority, visibility, and mutability.

Pure compiler services require explicit compilation, policy, environment, and sanitation snapshots. They do not read live Factorio globals through fallback paths.

Production may retain efficient trusted references. Validation mode wraps immutable records with mutation sentinels or read-only proxies.

Publication uses a deterministic body-then-envelope model rather than a telemetry fixed-point loop.

## Recipe And Process Semantics

Introduce `RecipeFactV3` with normalized variant quantities, primary and secondary products, productivity-sensitive quantities, returned containers, catalysts, ignored-by-productivity values, self-intersection, probability/correlation, surface and quality constraints, machine/category compatibility, unlock technologies, existing owners, and source mod/version.

Build a bipartite item/fluid-to-recipe process graph and classify:

```text
forward manufacturing
equivalent alternate production
extraction
separation
recycling
recovery
voiding
catalyst regeneration
reversible conversion
biological reproduction
transmutation
correlated multi-output process
```

Generic automatic admission remains limited to proven forward or equivalent manufacturing inside explicit applicability envelopes. Complex Angel, Py, K2 matter, Space Exploration recovery, recycling, catalyst, biological, and correlated-output processes remain review-only until cycle, catalyst, byproduct, and net-flow proofs exist.

## Runtime Feature Kernel

Replace the central manually edited runtime router with versioned `RuntimeFeatureSpec` records. Each record declares state schema, events, lifecycle hooks, force/player scope, target requirements, migrations, disable behavior, and handler module.

Adding a runtime feature should require one specification, one handler, and a migration only when its state schema changes.

## Control Plane And Developer Tooling

First modularize the current PowerShell control plane behind stable component ABIs. Do not begin with a language rewrite. Then establish a typed cross-platform `mirctl` kernel:

```text
tools/mirctl/
  cli
  manifests
  hashing
  package
  scenario
  process
  evidence
  impact
  cache
  release
  backport
  reports
```

`scripts/mir.ps1`, `mir.cmd`, and `./mir` become thin launchers. Platform-specific process and installation behavior lives in Windows, POSIX, GitHub Actions, and filesystem adapters.

Every command owns a typed argument schema, defaults, config sources, exit codes, JSON output schema, help text, and side-effect class. Every major command supports `--json`, `--explain`, `--dry-run`, and `--output`.

Every run emits structured JSON Lines events including run start, selection, cache decisions, process lifecycle, artifacts, assertion failures, and completion.

## Test And Evidence Architecture

Replace nested suites with atomic tasks:

```text
docs.schema
docs.generated
architecture.files
architecture.dependencies
compiler.unit
compiler.contract
settings.contract
locale.contract
package.build
package.composition
scenario.<id>
upgrade.<id>
performance.<lane>
release.delta
manual.review
seal
```

Profiles select nodes. Aggregate gates inspect results and never rerun children.

Generate the impact graph from Lua imports, command dependencies, schemas, target capabilities, fixtures, scenario assertions, package roots, changesets, and evidence producers. Unknown paths select a conservative profile. Mutation tests must prove the selector catches provider, graph, setting, locale, target-adapter, and release-manifest changes.

Separate expensive observations from cheap evaluations. One exact Factorio environment load produces a reusable immutable observation; independent evaluators check graph safety, ownership, sanitation, science/labs, compatibility, quality, progression, and release claims.

Exact runtime cache keys include candidate content, Factorio binary, official mods, third-party closure, startup settings, scenario declaration, fixtures, harness, target profile, and producer trust class. Every reuse decision explains why it is valid.

After a failure, rerun the failed task, its prerequisites, and tasks whose effective inputs changed. Run the complete no-reuse protected profile once after final freeze.

Resource classes are `cpu-light`, `io-heavy`, `factorio-runtime`, `performance-exclusive`, `manual`, and `protected`. Performance work runs alone on the qualified host.

Development tiers:

- T0: syntax, formatting, schema, generated drift.
- T1: pure unit and property tests.
- T2: package plus Base and Space Age smoke.
- T3: exact affected scenarios.
- T4: maintained ecosystem and performance campaigns.
- T5: complete no-reuse protected release qualification.

## Release Governance

Move toward immutable per-release records and a small current pointer:

```text
.mir/releases/records/3.3.0.json
.mir/releases/records/2.6.0.json
.mir/current.json
```

Separate stable target capability profiles from version-specific release transitions. A release transition owns prior release, candidate release, migration fixtures, approved delta, performance baseline, manual scope, and upgrade expectations.

Generate branch roles, release wave, distribution inventory, current candidate, release-note identity blocks, TODO release status, publication checklist, and backport source lock from those records. Human prose may explain behavior but must not independently copy mutable hashes, byte counts, entry counts, or states.

Use an explicit release state machine:

```text
draft
→ package-frozen
→ focused-green
→ full-local-green
→ manual-approved
→ protected-green
→ sealed
→ promoted
→ published
→ public-bytes-verified
```

Every transition has an immutable receipt.

Each package-visible change carries a machine-readable changeset declaring behavior class, affected contracts, stable IDs, migration effect, test impact, Factorio 2.0 disposition, release-note text, and required evidence.

## Target Projection And Backports

The long-term target build is:

```text
immutable modern release
+ immutable target baseline
+ target capability profile
+ executable adapter registry
+ release overlay
→ deterministic target tree and package
```

Adapter classes cover metadata, dependency floors, prototype shapes, product fields, science kinds, effects, `mod-data` omission, runtime storage, feature omission, assets, migrations, and release text.

Every modern change declares one target disposition when implemented:

```text
portable-identical
portable-with-generated-adapter
target-native-equivalent
omitted-by-capability
finite-reconstruction
unsupported-with-evidence
release-governance-only
```

The final 2.6 package must be buildable from immutable inputs without an existing target branch. A target-first/source-second merge remains the provenance record, while target branches are disposable qualification workspaces.

Branch-loss rehearsal deletes and recreates the target workspace and requires identical ancestry, integration tree, archive hash, content hash, bytes, entries, target semantic report, and declared capability differences.

## Repository And Storage

Stop adding complete historical source trees, raw validation output, large logs, saves, and every candidate ZIP to the active repository. Keep compact manifests, commits, trees, package hashes, asset identities, and qualification summaries. Store future bulk artifacts in workflow/release assets, a dedicated archive repository, or mirrored content-addressed storage.

Do not rewrite public Git history to remove existing artifacts.

Use a local content-addressed run store:

```text
.mir/cache/
  objects/sha256/
  runs/
  closures/
  packages/
  saves/
```

## Compatibility Expansion

Each maintained ecosystem profile binds the Factorio binary, exact mod archives and hashes, dependency closure, startup settings, finalizer order, science and lab roles, external owners, accepted and denied families, expected sanitation, version envelope, performance envelope, and claim maturity.

Support claims progress independently through observed, startup-integrity-qualified, structural-integrity-qualified, generation-qualified, human-reviewed, balance/playability-qualified, and released-canonical.

Recommended qualification order after the platform stabilizes:

```text
AAI / OC / BZ
→ K2 / K2SO
→ Space Exploration
→ Bob
→ Angel
→ Py
→ broader compatible combinations
```

Promotion order:

```text
existing-stream attachment
→ exact external-owner cooperation
→ exact-profile technology
→ bounded structural envelope
→ specialized complex process only after process proof
```

## Release Segmentation

### 3.3.0 / 2.6.0 — Platform Fixed Point

- Freeze 3.2.2/2.5.0 semantic exports as golden fixtures.
- Establish canonical FeatureSpec and SettingSpec v2.
- Add typed target capabilities and composable provider protocols.
- Introduce policy fragments, typed claims, conflict traces, universal mutation plans, and a runtime feature registry.
- Separate observations from evaluations.
- Establish generated semantic impact and immutable release-transition records.
- Begin control-plane modularization and atomic test DAG migration.
- Build deterministic target projection.
- Preserve public behavior and stable IDs.

### 3.3.1 / 2.6.1 — Stabilization

- Fix extension, projection, profile, state-migration, batching, cache, portability, and tooling UX defects.
- Add physical immutability checks and typed context keys.
- Remove live-global fallbacks and publication fixed-point iteration.
- Move bulk history out of active development workflows.

### 3.3.2+ / 2.6.2+ — Semantic And Ecosystem Work

- Add RecipeFactV3 and process-flow classification.
- Expand reviewed corpora and exact ecosystem profiles.
- Improve family partitioning, candidate alternatives, quality scoring, and review queues.
- Continue dependency-cycle removal.

### 3.3.5 / 2.6.5 — Reviewed Promotion Wave

- Promote safe attachments, exact owners, bounded assembler/lab families, and selected exact material families.
- Keep unproven complex process families diagnostic or review-required.

## Acceptance Criteria

Platform acceptance requires:

```text
zero normalized gameplay delta during foundation migration
zero stable-ID delta
zero forbidden dependency SCCs
one canonical release authority
one typed control-plane kernel
one atomic test DAG
generated and mutation-tested impact selection
no duplicate atomic test execution
exact cache-hit explanations
all targets reconstructible from immutable inputs
no unique implementation knowledge on tmp branches
2.1 and 2.0 target packages independently qualified
```

Performance goals:

- No Factorio package-load regression.
- At least 50 percent lower median affected-development validation time.
- Static changed-file checks under 30 seconds when runtime is unnecessary.
- Focused static suite near two to three minutes.
- One Factorio load per exact environment followed by offline evaluations.
- Full no-reuse qualification retained for final protected release.

## Non-Goals

Do not:

- Mix the platform overhaul into C24 or P9.
- Enable broad unsafe generation by default.
- Treat startup success as full semantic support.
- Rewrite the assurance system in another language before its ABIs and task graph are stable.
- Use caches as release evidence.
- Use Factorio 2.1 evidence as Factorio 2.0 evidence.
- Preserve unique target knowledge only on a temporary branch.
- Rewrite public Git history to reduce storage.

## Definition Of Done

The architecture is successful when a new ordinary feature, setting, provider family, compatibility profile, runtime handler, test, or target is added by contributing a versioned record and focused implementation to the correct registry rather than editing central orchestration code.

Every MIR decision must be explainable from immutable facts, policies, claims, constraints, resolutions, operations, and evidence.
