# MIR 3.3 And 2.6 Convergence Platform Roadmap

> Historical architecture roadmap. MIR 3 now ends with the unified `.9` stabilization wave; viable platform ideas from this document are MIR 4 handoff inputs, not active MIR 3.3 or 2.6 release commitments.

This roadmap starts after MIR 3.2.5 is released and the MIR 2.5.5 feasibility decision is recorded. MIR 3.3 is the canonical behavior-preserving platform fixed point. MIR 2.6 is a generated, independently qualified Factorio 2.0 projection of the same semantic source.

The cross-release sequencing authority is the [MIR 3.2.5 to 2.6 convergence programme](../releases/3.2.5-to-2.6-convergence-programme.md). The public extension objective is specified separately in the [MIR Extension Protocol v1 roadmap](mir-extension-protocol-v1.md). The [ultimate convergence audit action register](../releases/ultimate-convergence-audit-action-register.md) records the corrections that are prerequisites or refinements for this roadmap.

## Audit completion ceiling

The platform fixed point is not complete until it has one acyclic authority graph, one logical-path resolver, referentially complete semantic domains, most-specific ownership, append-only release history, and separate semantic, authority, and qualification digests. Prototype writes must be planned operations executed only by lifecycle-specific executors. Runtime contributions require typed descriptors, deterministic dispatch, explicit state/migration ownership, bounded complexity, and continuous-versus-reload equivalence. Assurance must bind propositions to content-addressed observation slices and evaluator identities. Target packages must be deterministic projections with target-local law and qualification evidence.

These are acceptance constraints, not permission to pull 3.3 implementation into 3.2.5.

## Entry conditions

Before M0 begins:

- P11 assurance and the 2.5.0 stabilization decision are closed honestly.
- C31 remains immutable and unpublished.
- MIR 3.2.5 is publicly verified with exact 3.2.3 upgrade proof.
- The 2.5.5 feasibility gate has either produced a qualified release or a preserved deferral report.
- Exact 3.2.5 and latest qualified 2.5.x packages, semantic exports, runtime states, migrations, performance, and proof closures are frozen as baselines.

No 3.3 milestone may rewrite those baselines or use a temporary branch as the sole owner of target or verifier knowledge.

## Platform fixed point

MIR 3.3 converges current authorities into one content-addressed authority graph. It does not place a second compiler beside the current one.

Conceptual terms such as world, feature, policy, plan, and evidence are views over existing records and future graph nodes. They do not justify parallel writable `WorldIR`, `PolicyIR`, `PlanIR`, or Lua `EvidenceIR` authorities.

The platform layers are:

```text
versioned specification authorities
→ content-addressed semantic build graph
→ normalized world and process facts
→ sealed safety plus configurable policy
→ typed claims and deterministic resolutions
→ specialized lifecycle plans and executors
→ runtime state and migrations
→ target projection
→ assurance, release, and publication
```

## Versioned authority system

Every stable authority declares logical ID, namespace, schema and semantic version, minimum reader/writer, lifecycle, owner, semantic/authority/qualification identities, dependencies, and target dispositions.

Identity classes remain distinct: feature, Factorio prototype, policy, setting, operation, runtime namespace, extension contribution, evidence object, and release record.

Lifecycle is explicit:

```text
experimental
reviewed
stable
deprecated
retired
tombstoned
removed
```

A stable feature cannot disappear without rationale, replacement or tombstone, setting/profile migration, save-state handling, target dispositions, documentation, compatibility impact, and a release transition.

## Feature manifests and settings

`FeatureManifest` is an aggregate index over independently owned identity, semantics, balance, settings, policy, presentation, target, runtime, migration, and proof fragments. Changing one fragment invalidates only its semantic dependants.

Static `FeatureTypeSpec` records may participate in the settings stage. Data-stage `FeatureInstance` records describe occurrences resolved from final prototypes. Dynamic instances cannot create startup settings retroactively; they use family settings, predeclared feature settings, sparse profiles, modpack profiles, or static contributions published by an extension in the settings stage.

Each `SettingSpec` owns stable ID, Factorio representation, semantic type, stage/scope, default source, range, target support, visibility, profile participation, override strategy, safety constraints, locale, documentation, aliases, and proof obligations.

Profile layering is:

```text
safe defaults
→ target defaults
→ ecosystem profile
→ modpack profile
→ user base profile
→ explicit user overrides
→ hard safety clamp
```

Every effective value reports its origin, previous/default value, constraints, clamp status, activation, and reason. Sparse profiles store differences and preserve unknown future fields.

## Semantic build graph

Every graph node declares input authorities, semantic reads and writes, implementation ABI, output schema, and output digest. The graph connects specification, generated Lua, compiler records, plans, target projection, package, observations, evaluations, and release proof.

It becomes the basis for incremental generation, impact selection, cache identity, proof reuse, backport invalidation, documentation generation, release explanation, and public compatibility diffs. File-path rules remain a conservative fallback.

Proof reuse requires:

```text
changed transitive writes
∩ proof transitive reads
= empty
```

The mutation journal also proves observed writes are a subset of declared writes. An undeclared write is release-blocking.

## Safety and policy

The sealed SafetyKernel owns target and schema validity, effect validity, one effective owner, technology graph safety, science/lab reachability, process/economy safety, operation cardinality, migration identity, runtime determinism, and public artifact budgets.

The configurable PolicyEngine chooses among legal outcomes: owner, science, prerequisites, cost, effect scale, enablement, presentation, profile, compatibility preference, and preview/apply. Profiles and extensions cannot widen the safety envelope.

Claims are partitioned by stage, subject type and ID, field path, conflict key, and target. Each field uses a registered merge law rather than one global priority. Operators declare algebraic properties and emit resolution traces containing facts, claims, authority, constraints, rejected alternatives, selected result, reasons, evidence, and fingerprint.

Do not create a general-purpose all-to-all solver.

## Specialized lifecycle plans

Use one common operation envelope containing ID, source, subject, authority, requirements, conflict key, precondition, desired state, postcondition, target requirements, and evidence.

Compile the envelope into specialized plans:

```text
SettingsPlan
PrototypeNormalizationPlan
PrototypeMutationPlan
RuntimeRegistrationPlan
MigrationPlan
TargetProjectionPlan
PublicationPlan
```

Each lifecycle has a dedicated executor and failure semantics. Every prototype write becomes a governed operation with exact preconditions, postconditions, declared writes, and one terminal journal result. Missing, duplicate, undeclared, or out-of-plan work fails closed.

## CompilerContext completion

The endpoint is explicit context in pure compiler code, typed services and keys, registered state schemas, phase-bounded mutability, structural sharing, memoized record identities, copy-on-write modification, defensive copy only at import/export boundaries, and single-pass final telemetry.

Global active-context access is restricted to the outer Factorio stage adapter and removed from pure domain logic.

## Runtime and migration kernel

A runtime feature contribution declares version, requirements, state namespace/schema, event subscriptions and filters, handler operator, determinism, target support, and complexity.

The generated runtime kernel registers each event once, orders subscribers deterministically, filters before dispatch, isolates state namespaces, tracks schemas, executes unambiguous migration paths, rejects duplicates, enforces budgets, emits structured diagnostics, and exposes read-only status.

Migration classes are reversible, forward-only nondestructive, forward-only destructive, repair-only, and tombstone. Tests compare continuous execution with save/reload continuation and require equivalent relevant state and outcomes.

## Process and economy safety

`ProcessIR` is derived from canonical recipe and relationship facts. It does not rescan prototypes as an independent truth.

It models items/fluids, processes, quantities, probability and correlation, productivity sensitivity, ignored quantities, catalysts and returned containers, recycling/recovery, quality/spoilage, surface and machine constraints, unlock paths, owners, and source identity.

Classifications include forward production, extraction, separation, alternate equivalent routes, recycling, recovery, voiding, catalyst regeneration, reversible conversion, biological reproduction, transmutation, and correlated multi-output processes.

Relevant strongly connected components require expected and conservative net yield, external resources, catalyst preservation, productivity amplification, recycling equilibrium, quality conversion, and protected-resource checks. A positive-yield loop certificate is hard safety. Confidence may rank review; it cannot overrule a failed certificate.

## MEP-1 extension platform

MEP-1 is required for the platform fixed point. It provides host-neutral declarative envelopes, unique 2.1 `mod-data`, portable stage-bus transport, legacy adaptation, capability negotiation, compatibility/profile fragments, bounded declarative providers, sealed safety, field-specific conflicts, inventory, diagnostics, SDK, offline tooling, and fork conformance.

Transport details remain outside the semantic compatibility policy authority. Trusted code adapters are experimental, immutable-input/data-output only, exact-archive-bound, and have no mutation authority.

See [MIR Extension Protocol v1 Roadmap](mir-extension-protocol-v1.md).

## Target projection

Evolve target profiles into a machine-derived structural capability certificate, hand-authored semantic policy, and adapter bindings for normalization, emission, runtime, assets, transport, and release overlay.

Required laws are:

- Round trip: `normalize(emit(semantic)) == semantic`.
- Preservation: unowned source fields remain unchanged.
- Idempotence: emitting the same desired state twice is stable.
- Locality: one semantic change leaves unrelated fields unchanged.
- Target parity: normalized target output equals its declared target-neutral disposition.

Unknown modded fields are preserved outside explicitly owned paths.

Every modern change declares `portable-identical`, `portable-with-adapter`, `target-native-equivalent`, `omitted-by-capability`, `target-specific`, `tooling-only`, or `unsupported-with-evidence`.

## Assurance architecture

Keep capture, compilation, realization, and evaluation identities independent. A parser or evaluator fix may replay sound observations; a changed Factorio/mod closure requires environment capture onward; a changed package reruns affected realization; a target-adapter change reruns target projection and target proof.

Every `ProofSpec` states proposition, subject, scope, observations, evaluators, semantic reads, and freshness. Proof objects record inputs, observation/evaluator identities, outcome, producer trust, freshness, and revocation.

Use content-eternal, environment-bound, candidate-bound, transition-bound, protected-release-fresh, and always-fresh classes. Revocation invalidates only the affected proof layer.

Partition observations into recipe, process, technology, science/lab, owner, settings, runtime, diagnostics, presentation, locale, and package Merkle slices.

Optimization may choose a deterministic proof cover over required obligations and compatible environment observations. It may reduce redundant capture; it cannot omit proof.

A pass and failure for one exact fingerprint creates a nondeterminism incident and blocks release. Do not retry until green.

Every escaped ecosystem defect is minimized into an exact lock, synthetic fixture, regression proof, incident record, and claim update.

## Control Plane evolution

Do not rewrite Control Plane v5 immediately. Stabilize record and command ABIs, split pure domain logic from process adapters, require structured results, run replacement components in shadow, prove plan/evidence equivalence, promote one component at a time, and retain platform-specific PowerShell adapters where useful.

Architecture authority is schema plus ABI plus proof contract, not implementation language.

The eventual command surface includes status, change explanation, generation, generated drift, compile, plan explanation, changed-proof selection, reuse explanation, evidence audit/revocation, profile validation, compatibility reports, target projection, release diff, and qualification. Major commands support JSON, explanation, dry run, and explicit output.

## Documentation and continuity

Generate settings, costs, features, target capabilities, claims, proof matrix, dispositions/reasons, migrations, API compatibility, composition, release identity, coverage, and target omissions from typed authorities.

Human-authored ADRs explain why authorities, boundaries, merge laws, and target decisions exist.

Every stable release archives source, Git bundle, toolchain lock, generator, schemas, SDK, reference extensions, vectors, target profiles, migrations, runbooks, evidence roots, and public identities. Runtime and startup never depend on a live central MIR service.

## Release segmentation

### MIR 3.3.0

Behavior-preserving platform fixed point: authority graph, schema lifecycle, settings generation, safety/policy boundary, MEP-1 declarative API and SDK, governed plans, runtime/migration foundation, assurance completion, target projection capability, and exact old/new parity. No broad default-on speculative generation.

### MIR 3.3.1

Stabilize profiles, runtime state, extension edge cases, migration tooling, evidence selection, target adapters, locale generation, claim expiry, support exports, builder UX, and community feedback.

### MIR 3.3.2

Optimize structural sharing, identity memoization, canonicalization, observation reuse, environment batching, CI, evidence storage, and diagnostics; add declarative family providers and optional experimental trusted adapters.

### MIR 3.3.3-3.3.5

Promote reviewed attachments, exact owners, exact-profile technologies, bounded structural manufacturing, material families, and process families only when economy certificates exist.

### MIR 2.6.0

Project exact 3.3.0 semantics onto the latest qualified 2.5.x baseline using Factorio 2.0 capabilities and adapters. Require deterministic reconstruction twice, branch-loss rehearsal, direct baseline upgrade, target laws, feature/omission inventory, cost/disposition parity, runtime migration, exact ecosystems, performance, manual review, protected seal, governed `legacy` promotion, and public-byte verification.

## Acceptance criteria

- Zero normalized gameplay delta during foundation cutover.
- Zero stable-ID delta.
- Zero direct prototype mutation outside executors.
- Zero forbidden dependency cycles at the platform fixed point.
- One canonical release and target-projection authority.
- One atomic proof DAG with no duplicate task execution.
- Generated and mutation-tested impact selection with zero false negatives.
- Exact explanations for every cache reuse.
- MEP-1 compatibility without a central service or official host dependency.
- Every target reconstructible from immutable inputs.
- No unique implementation knowledge on temporary branches.
- Independently qualified Factorio 2.1 and 2.0 packages.

## Non-goals

Do not enable broad unsafe generation, treat startup success as semantic support, rewrite the verifier before ABI stability, use caches as proof, reuse Factorio 2.1 runtime evidence as Factorio 2.0 qualification, expose arbitrary extension callbacks, preserve unique target knowledge on temporary branches, or rewrite public history.

The platform is complete when an ordinary feature, setting, compatibility fragment, provider family, runtime handler, proof, or target is added through one versioned contribution and focused implementation in the correct authority without editing central orchestration lists.
