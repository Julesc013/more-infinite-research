# MIR 4.2 nine-target candidate and playtest matrix

This page turns the current nine-target release-cut selection into a reviewable preparation matrix. It does not allocate a candidate, freeze a source, authorize support, change viewer behavior, or authorize a release transition. The [release runbook](../RELEASE-RUNBOOK.md) and the [nine-target release-cut programme](../../.mir/releases/governance/mir4/MIR42-Nine-Target-Release-Cut-ProgrammeV1.json) remain the controlling authorities.

## MIR 4.2.1 private construction

The existing constructor accepts `-SourceVersion 4.2.1` and selects the ordered nine targets by default. An explicit four-target selection is rejected for that source version. Use `tools/commands/release/New-MIR42FourTargetCandidate.ps1 -RepoRoot <primary-checkout> -FinalSourceCommit <exact-clean-commit> -BuildId <unique-id> -SourceVersion 4.2.1 -OutputRoot <approved-build-path>` after checking actual resource capacity. The constructor builds serial A/B copies through the existing materializers, records deterministic archive/content equality and custody, and writes `MIR42FourTargetDeterministicCandidateManifestV2`. It does not run native qualification, sign, seal, tag, promote or publish.

The expected distribution versions, in target order, are `4.2.21001`, `4.2.20001`, `4.2.11001`, `4.2.10001`, `4.2.01701`, `4.2.01601`, `4.2.01501`, `4.2.01401` and `4.2.01301`. The final two digits encode source patch 1. Historical target records and adapter bindings retain their frozen baseline identities; the codec projects the requested output separately. Current presentation templates supply the authored `4.2.1` changelog entries and upgrade guidance, preserving prior entries and the README catalogue. The package writer adds only the numeric/source identity to the README and preserves an already-current authored changelog unchanged. Qualification status belongs to the external candidate and release evidence, so publication must not rewrite the accepted package's prose. The `4.2.0` constructor and v1 schema remain available; reproducing a historical package requires its pinned source rather than today's presentation templates.

The acceptance test is registered as `static.mir42-candidate-construction` in the development and nine-target evidence profiles. Its schema fixtures and modern materializer stubs test contracts; actual package and native qualification evidence must bind the real nine ZIPs from the exact accepted source. Downstream evidence, signing, promotion and publication consumers need their own explicit current-version acceptance before a constructed v2 manifest can pass those transitions.

The qualification input reader now selects the v1/source `4.2.0` or v2/source `4.2.1` contract from the manifest. It verifies source and row bindings, expected distribution identities, actual ZIP hashes and metadata, and frozen historical record, terminal-seal and predecessor custody. A self-hashed row with the wrong source version or row schema is refused. Historical record validation uses its original CCC00 identity while the requested package identity uses CCC01. The portable constructor test supplies terminal predecessor inventory fixtures because hosted CI has no delivered terminal ZIPs; that control establishes input contracts, not executed predecessor custody or native qualification. The new reader supplies no release acceptance.

The independent rehasher also selects the versioned construction contract and binds row schema, kind, source version and reconciled distribution identity. Its input controls use actual constructed rows and ZIPs, a counted engine-lookup fixture and an intentionally mismatched predecessor. They verify both source versions reach the required predecessor refusal and that malformed rows remain refused even when the supplied upstream row hash is rebound. These controls create no accepted rehash output and run no engine. Actual independent rehash still requires candidate-bound upgrade receipts, logs, exact engines and predecessor custody.

The criterion writer carries the separately validated row package fingerprint into its source binding. Package-exclusion and deterministic-reconstruction observations accept the exact v1 or v2 construction manifest bytes, require the matching schema/kind descriptor, and refuse a reformatted copy even when its canonical record hash is unchanged. Writer tests use the real row shape and preserve performance-scope refusals for both manifest versions. Construction criteria establish only their named packaging propositions. Native criteria, complete release acceptance, engine qualification and later release consumers still require their own evidence and current-version work.

The existing manifest-driven upgrade harness now specializes its historical continuity fixture for either the exact MIR 3 terminal predecessor or an earlier same-target MIR 4.2 maintenance package. This admits the five historical `CCC00` → `CCC01` transitions while refusing equal versions, downgrades, other target codes and malformed identities. The shared distribution codec validates the selected versions; the fixture retains its engine-specific research, progress, bonus and two-reload assertions. Focused host tests establish transition selection only. Actual published 4.2.0 predecessor custody and candidate-bound native execution remain required before historical 4.2.1 upgrade acceptance.

The native campaign runner now selects the same versioned construction contract and derives all nine candidate destinations through the existing codec. Its source-only envelope tests retain v1 four-target and nine-target inputs, accept complete v2 nine-target inputs and refuse partial, misbound or incorrectly hashed manifests. Historical descriptors project CCC01 destinations while retaining their exact terminal predecessor, engine and target-record locks. The runner still checks clean exact source, package authority, actual archives, installed engines, published predecessor custody and resource admission before execution. No envelope or descriptor check is a native pass.
