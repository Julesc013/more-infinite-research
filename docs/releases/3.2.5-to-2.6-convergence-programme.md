# MIR 3.2.5 To 2.6 Convergence Programme

This is the canonical cross-release programme joining the immediate MIR 3.2.5 convergence release, the conditional MIR 2.5.5 Factorio 2.0 projection, the MIR 3.3 convergence-platform fixed point, and MIR 2.6. The release-specific record for 3.2.5, the architectural 3.3/2.6 roadmap, and the MEP-1 roadmap remain the detailed authorities for their own scopes. The [ultimate convergence audit action register](ultimate-convergence-audit-action-register.md) refines this programme with the final audit findings and typed open obligations.

This document is planning and sequencing authority. It does not freeze a package, create a candidate, advance a release state, transfer evidence, qualify a compatibility claim, or authorize prototype mutation.

## Executive decision

The programme is:

```text
1. Reconcile the P11 protected-evidence defect and close 2.5.0 stabilization.
2. Keep 3.2.4 unpublished and preserve C31 as an immutable superseded baseline.
3. Deliver one compatible MIR 3.2.5 release directly from public MIR 3.2.3.
4. Assemble 3.2.5 from small independently validated vertical slices.
5. Project each slice toward Factorio 2.0 while its semantics are still visible.
6. Publish MIR 2.5.5 only if the deterministic projection-feasibility gate passes.
7. Freeze the qualified 3.2.5 and latest 2.5.x behavior as the 3.3 baselines.
8. Build MIR 3.3 through shadowed, reversible changes to current authorities.
9. Make MEP-1 a first-class 3.3/2.6 release objective.
10. Generate MIR 2.6 from the exact 3.3 semantics and qualify it independently.
```

The release train is intentionally asymmetric. MIR 3.2.5 is planned. MIR 2.5.5 is planned conditionally and must be skipped if it would require a second compiler, duplicate policy authority, uncontrolled manual adaptation, or incomplete Factorio 2.0 proof.

## Decisions that resolve earlier alternatives

| Question | Decision |
| --- | --- |
| Publish 3.2.4? | No. Preserve C31 immutably as superseded and unpublished. |
| Is 2.5.5 unconditional? | No. Work toward it continuously, but create a release candidate only after feasibility passes. |
| Add parallel `WorldIR`, `PolicyIR`, `PlanIR`, or Lua `EvidenceIR` authorities? | No. Treat those names only as conceptual views and evolve the existing snapshot, policy, plan, result, journal, and external evidence authorities. |
| Rewrite Control Plane v5? | No immediate rewrite. Stabilize ABIs, separate pure logic from adapters, shadow replacements, and promote components one at a time. |
| Use one executor for every lifecycle stage? | No. Use one common operation envelope with specialized settings, prototype, runtime, migration, target, and publication plans and executors. |
| Treat `mod-data` as the extension API? | No. It is one transport for a host-neutral semantic protocol. |
| Run every test from scratch during development? | No. Reuse exact trusted proof and run the affected closure; run one complete protected no-reuse qualification after final freeze. |
| Expand 3.2.5 into the complete 3.3 platform? | No. 3.2.5 is a bounded convergence release with an explicit scope firewall. |
| Does reserving `C32` create a candidate? | No. `C32` is a monotonic floor until exact source or package identity is frozen; observations and proof cannot bind to a reservation. |

## R0: P11 assurance reconciliation

P11 is an immutable public package. Its outstanding work is an assurance closure, not permission to alter the published tag or archive.

The leading diagnosis is an evidence transport, aggregation, attempt-identity, or index-reconstruction defect because retained workers produced successful observations while the final aggregate treated the evidence set as empty. The response is to salvage immutable observations, repair their custody and evaluation path, and rerun only missing or invalid proof.

Every worker result must have an immutable manifest binding context, task fingerprint, environment, attempt, producer trust, content-addressed objects, and transport completion. Aggregation must verify the context and object digests, ingest objects atomically, rebuild indexes from objects, apply revocation, reject ambiguity, and evaluate the required proof closure. A failed aggregate must never erase or make successful worker observations undiscoverable.

Use distinct terminal categories:

```text
TRANSPORT_FAILED
OBSERVATION_FAILED
OBSERVATION_INCOMPLETE
EVALUATION_FAILED
PROOF_INCOMPLETE
PROOF_FAILED
INFRASTRUCTURE_FAILED
NONDETERMINISTIC
PASSED
```

A retry receives a new coordination-attempt identity while retaining the same immutable semantic context when candidate, target, transition, test definitions, environment locks, and control-plane ABI are unchanged. It may adopt exact completed objects and matching active workers. Mutable job status is never aggregate evidence.

P11 exits R0 only when protected qualification, post-publication seal, promotion-admission reconciliation, and the stabilization decision are recorded, or when a reproduced package defect justifies a minimal 2.5.1 with its own independent proof.

## R1: C31 preservation

C31 must not be renamed, edited, deleted, repackaged as 3.2.5, or moved backward through the release state machine. `.mir/releases/closures/3.2.4-C31.json` owns its exact immutable identity and closure disposition.

C31 remains useful as:

- The exact research-cost implementation baseline.
- A source of golden vectors, fixtures, performance observations, and semantic comparisons.
- Proposition-specific evidence only when every effective input and proof identity still matches.

C31 candidate-bound release proof does not qualify C32 or any later package. The public 3.2.5 comparison baseline is 3.2.3, while C31 is development lineage.

## R2-R4: MIR 3.2.5

### Public contract

MIR 3.2.5 is a substantial internal convergence release that preserves the 3.2.3 public patch-line contract:

- No removed or renamed setting IDs.
- No removed technology IDs without a governed migration or tombstone.
- No stable stream-ID changes.
- No breaking profile format or public extension behavior.
- Neutral defaults for every new setting.
- Existing profiles remain readable and unknown future fields survive round trips.
- Default behavior equals 3.2.3 except for named, approved, fixture-backed compatibility corrections.
- The public upgrade is 3.2.3 to 3.2.5; C31 to C32 is development continuity, not a public promise.

### Slice A: complete research-cost models

Retain one canonical formula:

```text
cost(L) = (B + A * (L - S)) * G ^ (L - S)
```

The values derive fixed, linear, exponential, and hybrid models without a redundant selector. Completion requires separate semantic and qualification identities, algebraic monotonicity proof, numeric operating-envelope and overflow tests, bounded external-formula parsing, cross-language golden vectors, engine-realized values, profile migration, continuous-versus-reload equivalence, and exact default parity with 3.2.3.

Finite samples remain useful characterization, but they are not the primary proof of a mathematical invariant.

### Slice B: derived compatibility dispositions

Disposition reporting is a read model over existing authorities. It must not create a second writable truth beside static visibility, `TechnologyCatalog`, `CompilerResult`, `GenerationPlan`, `CompilationPlan`, `TransformationPlan`, `MutationJournal`, realized prototypes, compatibility claims, and environment identity.

Each subject has one terminal outcome:

```text
MIR_MATERIALIZED
NATIVE_ADOPTED
EXTERNAL_PRESERVED
REVIEWED_REPLACED
DISABLED
OMITTED_NO_MEMBERS
OMITTED_UNREACHABLE
OMITTED_LAB
OMITTED_TARGET
REVIEW_REQUIRED
FAILED
```

The report binds observed, planned, applied, and realized projections, source authorities, stable reason and remediation codes, semantic identity, and qualification identity. It must be impossible to write contradictory owner, technology, and presentation actions independently.

### Slice C: lifecycle separation

Settings-stage visibility may use only static stream metadata, active mod IDs, static compatibility metadata, target capabilities, and feature maturity. It cannot depend on final recipes, technologies, owners, labs, or `data.raw` facts that do not yet exist.

Prototype-stage applicability may use finalized recipes, safe members, owners, science, labs, prerequisites, graph safety, target capabilities, and satisfied finalizer-order contracts.

MIR controls presentation only for MIR-owned prototypes. It must not globally unhide external technologies. An external late finalizer that runs after MIR requires a satisfiable load-order contract or a downgraded claim; MIR cannot claim to observe future mutations.

### Slice D: proof-dimensional compatibility claims

Keep maturity, behavior, and scope independent. Add independent proof dimensions without converting them into one inflated claim level:

```text
LOAD
INTEGRITY
SEMANTIC
PROGRESSION
UPGRADE
CONFIGURATION_CHANGE
RECOVERY
INTERACTIVE
PERFORMANCE
```

Every assertion binds a subject, exact environment, proposition, dimension, status, definition ABI, evaluator ABI, observation digest, evidence references, freshness, expiry, and revocation state. Public claims are generated from non-revoked proof; prose cannot promote them independently.

### Slice E: exact environments and ecosystem profiles

An exact environment binds the Factorio binary and official data, enabled official modules, third-party archive identities, resolved dependency order, startup settings, MIR profile, bridge packages, target adapters, finalizer-order assumptions, expected owners and omissions, science and lab roles, sanitation, claim envelope, and performance envelope.

Use three separate support layers:

1. Generic structural support with conservative mod-name-independent facts.
2. Ecosystem semantic profiles for named policy families.
3. Exact version-qualified profiles for release evidence and bounded exceptions.

An everything-installed environment is a useful canary, but it cannot manufacture broad support claims for its members.

### Slice F: support, privacy, and localization

Ship a bounded support product before attempting a large GUI subsystem:

- Deterministic offline JSON.
- Localized summary-first text.
- Stable reason and remediation codes.
- Effective-setting value, origin, constraint, and clamp explanations.
- Compact data-stage diagnostics.
- Privacy-safe support bundles.
- Explicit truncation counts and resource limits.

Default exports remove usernames, absolute paths, save names, access tokens, unbounded prototype tables, and oversized logs. Diagnostics-off performs no new broad scan or mutation.

### Slice G: earned consolidation

Only refactor internals needed by slices A-F:

- Separate semantic, authority, and qualification identities.
- Normalize optional arrays to `[]` and reject null members.
- Consolidate duplicated settings metadata.
- Repair referential integrity for semantic domains and obligation aliases.
- Move remaining mutable run caches into `CompilerContext`.
- Make reports consume existing compiler artifacts instead of rescanning `data.raw`.
- Separate target-neutral report semantics from Factorio 2.1 and 2.0 transports.
- Remove duplicate graph capture only after shadow equivalence.
- Reduce deep copying and canonicalization only where measurement justifies it.

### 3.2.5 scope firewall

Defer these to 3.3 or later:

- The semantic build graph as a complete authority system.
- Full physical SafetyKernel and PolicyEngine separation.
- `ProcessIR` and economy-loop certification.
- Stable public third-party extension protocol and SDK.
- General-purpose solvers, arbitrary callbacks, or broad rule engines.
- Complete target package generation.
- Full runtime registry cutover.
- Mass directory reorganization.
- Control-plane language replacement.
- Broad default-on experimental family generation.

Do not enable generic productivity for K2 matter conversion, Space Exploration recovery or arcospheres, Angel sorting and recovery, Py biological or catalyst loops, voiding, transmutation, correlated multi-output processes, or unknown recovery. They remain diagnostic or review-gated until process and economy proof exists.

The feasibility result has only two valid terminal outcomes: `passed`, which admits `255-F1`, or `deferred-with-evidence`, which records why the bridge is unsafe and moves the missing capability into the 3.3/2.6 programme. There is no deadline-based exception and no partial release presented as parity.

### Feasibility gate

Proceed only when all of these are true:

1. Every 3.2.5 change has a Factorio 2.0 disposition.
2. Existing or explicitly reviewed adapters can express each portable semantic.
3. No parallel compiler is required.
4. No duplicate policy authority is required.
5. Stable IDs and profile semantics remain valid.
6. Cost and disposition behavior is equivalent or explicitly omitted.
7. Upgrade and runtime migration behavior is defined.
8. Reconstruction from immutable inputs is deterministic.
9. Required exact Factorio 2.0 closures exist.
10. Target performance is acceptable.

The construction equation is:

```text
latest qualified 2.5.x baseline
+ immutable MIR 3.2.5 semantic source
+ Factorio 2.0 capability certificate
+ reviewed target adapters
+ release transition
= exact MIR 2.5.5
```

If R0 produced 2.5.1, that release is the target baseline. Otherwise use 2.5.0.

### 2.5.5 proof

Require dual-parent provenance, deterministic projection twice, branch-loss reconstruction, exact tree and package identity, direct latest-2.5.x upgrade, cost and disposition parity, target settings, runtime migration, exact Factorio 2.0 environments, performance, manual review, protected qualification, target seal, governed promotion to `legacy`, publication, and public-byte verification.

When feasibility fails, do not force a release. Preserve the gate report as an explicit 3.3/2.6 design input.

## Assurance model

Keep four distinct proof identities:

```text
CaptureKey     = Factorio + exact mod closure + settings + finalizer order
CompilationKey = captured snapshot + policy + compiler ABI
RealizationKey = accepted plan + exact candidate + target executor
EvaluationKey  = observation + assertion/evaluator ABI
```

Use explicit freshness classes: `content-eternal`, `environment-bound`, `candidate-bound`, `transition-bound`, `protected-release-fresh`, and `always-fresh`. Revocation may invalidate a producer, evaluator, or canonicalizer without discarding unrelated sound observations.

Partition large observations into recipe, process, technology, science/lab, owner, settings, runtime, diagnostics, presentation, locale, and package slices. A proof references only the slices it reads.

Development tiers are:

| Tier | Purpose |
| --- | --- |
| T0 | Syntax, schema, formatting, and generated drift. |
| T1 | Pure unit, property, metamorphic, mutation, and differential proof. |
| T2 | Deterministic package plus exact Base and Space Age smoke. |
| T3 | Exact affected scenarios and transitions. |
| T4 | Maintained ecosystem, performance, and manual campaigns. |
| T5 | Complete protected no-reuse release qualification. |

During development, reuse only exact trusted proof, run changed semantic closure, adopt matching active work, and rerun failures or invalid prerequisites. After final freeze, run one complete protected no-reuse qualification.

## Maintainership rules

Every implementation slice follows:

```text
schema or contract
→ golden characterization
→ shadow producer
→ differential tests
→ target disposition
→ consumer integration
→ focused realization proof
→ documentation generation
→ cutover
→ old-path retirement after a released fixed point
```

Commits remain small by concern, establish schema before producer and producer before consumer, retain rollback points, avoid mass renames during semantic change, and never hand-edit generated views. Temporary shims declare owner, reason, replacement, introduced release, removal target, equivalence test, and expiry.

## Non-negotiable gates

- Zero prototype writes outside governed executors.
- Zero compatibility policy files with direct mutation authority.
- Zero global `CompilerContext` access in pure domain code at the 3.3 fixed point.
- Zero unversioned public schemas or unnamespaced extension contributions.
- Zero dynamic startup settings created after the settings stage.
- Zero external override of hard safety.
- Zero unclassified target disposition or package path.
- Zero undeclared semantic domain or observed write outside its declared write set.
- Zero runtime state without migration and determinism policy.
- Zero stale claim presented as current.
- Zero proof derived from revoked evidence.
- Zero impact-selector false negatives.
- Zero unique target knowledge on a temporary branch.
- Zero candidate rebuild between qualification and publication.
- Zero lost completed worker evidence.

## Explicit non-goals

Do not publish 3.2.4 because its ZIP exists, repurpose C31, build 3.2.5 as one mega-commit, force 2.5.5, add parallel compiler authorities, replace the control plane before ABI equivalence, build an unrestricted rule engine, let extension code mutate prototypes through MIR, let profiles override hard safety, globally unhide external technologies, infer semantic support from a load, reuse Factorio 2.1 runtime proof as Factorio 2.0 qualification, retry nondeterminism until green, treat job status as evidence, rebuild during publication, or rewrite public history.
